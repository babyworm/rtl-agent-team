## Per-claim notes

### #1 No remote execution backend: CONFIRMED (one sub-claim imprecise)

- tool-runner `run_tool()` 131-156: `if command -v "$tool" ...; then "$tool" "$@"` (136-139), else Docker checks, then `docker exec "$_TOOL_RUNNER_CONTAINER" "$tool" "$@"` (155). `check_tool_available()` 202-214 follows the same local-then-Docker order. `check_tool_licensed()` 218-237 calls bare commercial binaries locally.
- gen_config `tool_detect()` 80-109 tries three local strategies, not only `command -v`: an explicit `path` (84, `-f` and `-x`), then `env_source` via `bash -c 'eval "$1" >/dev/null 2>&1 && command -v -- "$2"'` (92-93), then `command -v` (102). All run on the local host; `env_source` is eval'd locally.
- Remote keywords: zero matches in code (sh/py/Makefile/mk/json/tcl) or markdown. A search for generic hooks (`*_PREFIX/_WRAPPER/_LAUNCHER/_EXEC/_RUNNER/_HOST/_CMD` env vars) found only `RTL_AWS_BATCH_RUNNER`. The other env knob is `RTL_EDA_IMAGE` (Docker image name).
- Sub-claim "only remote path is the AWS opt-in in run_regression.sh" is imprecise. There are also:
  - `skills/codec-rd-eval/scripts/aws_batch_submit.py` (boto3 `submit_job`), called from `run_eval.py:495-515` with `--mode aws-batch`
  - `skills/codec-conformance-eval/scripts/aws_batch_conformance.py`, called from `run_conformance.py:333-376`

  Both are built-in boto3 submitters with no `RTL_ALLOW_AWS` gate, used for codec C-model encode/decode runs, not EDA tools. For EDA tools, cocotb_reg is the only remote hook.
- How the AWS runner injection works (cocotb_reg:189-216):
  1. `--mode` must be `local` or `aws-batch` (168-171, else exit 2). Results and coverage dirs are created first (187).
  2. `aws-batch` requires `RTL_ALLOW_AWS` to equal `1` (190-194, exit 2 with "requires explicit opt-in").
  3. It requires `RTL_AWS_BATCH_RUNNER` to be non-empty (196-200, exit 2 "no AWS runner configured") and executable `-x` (202-205, exit 2).
  4. It then runs `exec "$RTL_AWS_BATCH_RUNNER" --seeds "$SEEDS" --sim "$SIM" --parallel "$PARALLEL" --tb-dir "$TB_DIR" --module "$MODULE" --results-dir "$RESULTS_DIR" --coverage-dir "$COVERAGE_DIR" --max-fail-rate "$MAX_FAIL_RATE"` (207-215).
- Properties of the injection:
  - The contract is argv only, with no eval.
  - `exec` hands off the whole job. The handler owns the exit status and must write `seed_*_results.json`, `results_*.json` and coverage itself. None of the local harvest/halt/report code (218-350) runs.
  - The plugin ships no handler; `tests/unit/test_regression_coverage.py` uses an echo stub.
  - The script is not deployed into projects. It is invoked as `{plugin_root}/skills/rtl-p5s-func-verify/scripts/run_regression.sh`, e.g. from `agents/p5s-func-verify-orchestrator.md:148` and `skills/rtl-p5s-func-verify-policy/SKILL.md:80-84`.
  - It covers cocotb only: the local path is `make -C "$TB_DIR" sim SIM=... RANDOM_SEED=...` (248), not run_sim.
  - Policy (`agents/p5s-func-verify-orchestrator.md:28-29`, `skills/rtl-p5s-func-verify-policy/SKILL.md:45-46`) allows `aws-batch` only when the user explicitly asks.
- Practical note: nothing in the injection is AWS-specific. Any executable works, so a site could plug an SSH/LSF handler into cocotb regressions today (`RTL_ALLOW_AWS=1 RTL_AWS_BATCH_RUNNER=/path/handler`).
- Generalization caveats:
  - Delegation is job-level, not per tool.
  - A per-command remote backend would need path translation (see the Docker path-mapping gap in #2), result retrieval, and faithful exit status.
- Minimal fix locations:
  - tool-runner `run_tool()` 131-156: add a backend branch with an argv contract like the AWS hook.
  - gen_config `tool_detect()` 80-109: add a remote probe.
  - Route run_sim `run_cmd()` 185-196, uvm_reg direct calls (compile 211-248, run 295-321), and the Makefile direct-tool targets through it.

- IEEE 1800 §20.2: the `$finish(n)` argument selects diagnostic verbosity (0/1/2), not an exit status.
- `$finish(1)` on failure/timeout:
  - unit_tb: 69 (timeout watchdog), 152 (`TESTS FAILED`)
  - integ_tb: 58, 123
  - repro_tb: 60, 91

There are zero `$value$plusargs` readers repo-wide. Templates hard-code `localparam int L_TIMEOUT = 100_000` (unit_tb:17) and `500_000` (integ_tb:17).
- Not in the report:
  - (a) Adding `-exitstatus` alone likely will not make `$finish(1)` non-zero, since it is a normal finish. Templates need `$fatal(1, ...)`, or runners need a log scan.
  - (b) Not VCS-only. run_sim propagates the raw simulator exit status for all 5 simulators (set -e; the `EXIT_CODE` at 550-554 is only reached on success) and parses no logs. Nothing in the repo consumes "ALL TESTS PASSED" or "TESTS FAILED".

  - (e) Downstream trust: the Rule 5 marker `.rat/state/rtl-verify-done` is `touch`ed by the agent, not the hook (e.g. `skills/rtl-orchestrate/SKILL.md:438`), so "Run complete (exit code: 0)" is the evidence it sees. The PPA smoke gate (ppa_orch:240-249) trusts the exit status of `make -C sim/${PPA_TOP} smoke 2>&1 | tee ...` without pipefail, which is tee's status.
  - (f) Makefile `sim_questa` and run_sim `run_questa` use `-do "run -all; quit -f"`, which also returns 0 regardless.
- Minimal fix locations:
  - TB templates: use `$fatal` for fail/timeout and read `$value$plusargs("timeout=%d", ...)` with L_TIMEOUT as the default. That means unit_tb 66-70 and 148-153, integ_tb 55-59 and 118-124, repro_tb 58-60 and 91, vcodec_tb 119-121.
  - run_sim `run_vcs` 446 (add `-exitstatus`), plus an optional run-phase log scan in `run_cmd`.
  - uvm_reg:295; Makefile 133 and 262.
