## Model facts that matter here

- In Claude Code the agent `model:` aliases resolve to `opus` → Opus 5.5, `fable` → Fable 5.1, `sonnet` → Sonnet 5, `haiku` → Haiku 4.5. The agent `effort:` field overrides the session effort; when absent the subagent inherits the session effort.
- Opus 5.5: thinking is always on and effort is the control. The API default is `medium` (Opus 5 defaulted to `high`); Anthropic reports Opus 5.5 at `medium` matching or beating Opus 5 at `high` on coding and knowledge work. At a given level it thinks more per turn than Opus 5, so `xhigh`/`max` are for measured gains only. Between-tool notes arrive as progress-update thinking blocks.
- Fable 5.1: gains are largest at higher effort (default `high`). "Prompts and skills written for prior models are often too prescriptive for Claude Fable 5.1 and reduce output quality" — A/B with step-by-step scaffolding removed. It writes fewer user-facing updates and benefits from grounded progress claims and asynchronous delegation. Price is 2.5x Opus 5.5 per token ($10/$50 vs $4/$20 per MTok).
- Both: prompts that push the model to reproduce its internal reasoning in the response text can be declined (`reasoning_extraction`). Fable 5.1 lists compile-check phrasing and lesser-known languages as false-positive triggers for its safeguards.

## Model/effort policy (decision D4, 2026-09-25)

| Tier | Role | `model` | `effort` |
|---|---|---|---|
| A | Architecture judgment | latest Fable (`fable`), or `opus` when the project chose Opus at initialization | max |
| B | Design, micro-architecture, coordination, result judgment | `opus` | max |
| C | Implementation (coding) | `opus` | xhigh |
| D | Mechanical work | `opus` | low |
| E | Anything else | `opus` | medium or higher |

Aliases track the latest release of each family (`fable` → Fable 5.1 and `opus` → Opus 5.5 today); no pinned model IDs. No agent uses Sonnet.

### Mechanism

- Effort is frontmatter-only. The Agent tool accepts a per-spawn `model` but no `effort`, and a frontmatter `effort` overrides the session effort. Every agent therefore declares its tier's `effort:`, and a user's `/effort` does not change agent effort.
- The architecture model is a project choice. rat-init-project asks once and writes `models.architecture` (`fable` | `opus`) to `rat_config.json`; projects initialized earlier are asked at their first architecture-phase run. Orchestrators that spawn tier-A agents pass `model="<models.architecture>"` on each spawn (the per-spawn parameter wins over frontmatter). Tier-A frontmatter is `model: opus`, `effort: max`, so a direct spawn outside an orchestrator still runs Opus at max.
- The initialization question states the trade-offs: Fable costs 2.5x Opus per token, runs longer turns at max, and requires 30-day data retention (organizations under zero data retention get a 400 on every Fable request). When a Fable spawn fails for access reasons, the orchestrator retries with `opus` and records the fallback in `rat_config.json` instead of retrying Fable on every spawn.
- "Fable at max or xhigh" resolves to max: effort cannot vary per spawn, and max also serves the Opus branch. A Fable-at-xhigh option would need a second definition of each tier-A agent; not planned unless requested.

### Spawn overrides to remove

27 spawn calls pass `model=` explicitly. All 20 `model="sonnet"` overrides reuse `arch-designer`, `rtl-architect` or `uarch-designer` for documentation — phase summaries and ADRs in `dse-orchestrator`, `p2-arch-orchestrator`, `p2-arch-team-orchestrator`, `p3-uarch-orchestrator`, `p3-uarch-team-orchestrator`, `spec-to-uarch-orchestrator`, `spec-to-uarch-team-orchestrator` and `uarch-to-verify-orchestrator` (e.g. `p2-arch-orchestrator.md:341`). Under D4 that work moves to `design-note-writer` (tier E, `effort: high`), whose scope widens from the Phase 6 note to phase summaries and ADRs; reusing a tier-A/B agent would run a one-page summary at max effort. The 7 `model="opus"` overrides in `p1-research-orchestrator` and `p2-arch-orchestrator` are replaced by `models.architecture` for tier-A agents and dropped elsewhere.

## Eval suite sketch (Phase 5a)

Layout per the plugin-evals doc: `evals/<case>/prompt.md` (+ optional `case.yaml`), graders under `evals/<case>/graders/`, results under `evals/<case>/results/` (gitignored).

- Routing: one case per intent class, English and Korean phrasings. Grader `type: tool_used`, `tool: Skill`, `input_match: '"skill"\s*:\s*"rtl-agent-team:rat-init-project"'`.
- Gate behavior: a fixture project with an RTL edit and no verification; graders check that the session does not end with a completion claim (`regex` on `last_message`) and that the verify runner ran (`tool_used` Bash with `run_sim`).
- Refusals: run representative agents on Opus 5.5 and Fable 5.1 and fail on any `reasoning_extraction` stop.
- CI form: `claude plugin eval . --trust-plugin --json results.json --threshold 0.8 --max-cost-usd <cap>`; exit 0 means every case met the threshold.

## Keep list (do not "clean up" these)

- Exact EDA command lines, gate sequences, destructive or ordering-critical steps — low freedom is correct there.
- Artifact contracts: required sections, iron-requirement schemas, RFC-2119 MUST in specifications.
- CRITICAL/MAJOR/MINOR as severity labels.
- Tool-grounded verification loops (lint → TB → sim, re-verify after fix). The Opus 5 advice to delete verification scaffolding targets prose self-checks, which this plugin does not use.
- Domain context: standard clauses, fixed-point rules, naming conventions. Context is never cruft.
