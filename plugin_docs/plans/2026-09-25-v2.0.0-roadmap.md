## 2. Findings beyond the report

F1–F4 undermine the enforcement model the plugin is built on; they come before any other v2 work.

- **F1. Stop gates cannot block.** `emit_stop_block` (`hooks/lib/hook-output-util.sh:27-31`) emits `{"continue":false,"decision":"block",…}`. Per the hooks reference, `continue: false` takes precedence and Claude stops. `rtl-verify-stop-gate.sh` (Rule 5), `rtl-skill-completion-gate.sh`, `stop-gate.sh` and `rtl-p6-cascade-gate.sh` therefore end the turn instead of returning the reason to Claude; only `rtl-coverage-exclusion-gate.sh` uses the working shape. 39 assertions in `tests/unit/test_hooks.py` and `plugin_docs/hook-development-guide.md:86` pin the wrong shape. `emit_block` (PreToolUse deny) also sets `continue:false`, halting the whole turn.
- **F2. Typed slash commands bypass every PreToolUse(Skill) hook.** They fire `UserPromptExpansion` (`expansion_type: "slash_command"`, `command_name`), which `hooks.json` does not register, so the completion loop, compliance state, spawn manifest and P5B entry block never engage.
- **F3. Rule 5 evidence is self-attested.** The agent `touch`es `.rat/state/rtl-verify-done` (`skills/rtl-orchestrate/SKILL.md:438`); the PPA smoke gate trusts `| tee` without `pipefail` (`ppa-optimizer-dc-orchestrator.md:240-249`).
- **F4. Fixes do not reach existing projects.** Stale `rat-version` markers (`run_lint.sh`/`run_cdc.sh` 0.7.7 after 12 content commits, `run_syn.sh` 0.11.3 after 7, none in `run_sim.sh`) and no caller passing `--update`.
- **F5. The Docker fallback cannot work.** Host paths are passed unchanged into a container that mounts the project at `/workspace`; `run_syn.sh` exits 127 before `run_tool`; the Makefile sources the bash-only library under `/bin/sh`.
- **F6. `env_source` and `tools.*.path` are detection-only.** No wrapper, Makefile rule or hook reads `rat_config.json`.
- **F7. Tool preferences are not honored downstream.** `SIM=verilator` hard-coded in the func-verify orchestrator; 11 agents hard-code Verilator and 2 Yosys; no route from `preferences.simulator` to UVM; preferences never refresh.
- **F8. Two hooks never fire.** `rtl-spawn-context.sh` and `rtl-audit-spawn-complete.sh` match `TaskCreate` but read the `Agent` tool's `subagent_type`.
- **F9. SpyGlass gaps beyond #10/#11.** `+incdir+`/`+define+` dropped, nested `-f` aborts, `run_goal` violations never fail the run, and `sg_shell` is ranked first for lint and CDC.
- **F10. Exit-status trust is simulator-wide.** Questa `-do "run -all; quit -f"` returns 0; `run_sim.sh` parses no logs.
- **F12. Hooks ignore a RAT project while the session is in a subdirectory.**
  - Claude Code reports the session's current directory as the hook `cwd`, and a `cd` persists.
  - `rat_project_dir` checks only `$CWD/.rat`, so after `cd rtl` every RAT hook exits early. The edit tracker records nothing and Rule 5 lets unverified RTL through.
  - Found by the 1a Task 3 review; fixed in 1a Task 7b.
- **F13. Team mode exempts every session from the Stop gates.**
  - The team skills write the literal `"<current_session_id>"` as the leader.
  - The hooks compare it with `CLAUDE_SESSION_ID`, which Claude Code never sets. It exports `CLAUDE_CODE_SESSION_ID`, and every hook input carries `session_id`.
  - So all five Stop gates skip for the leader too, while a team config exists. The team tests pass only because they set the unused variable.
  - Found by the 1a Task 3 review; fixed in 1a Task 7c.
- **F11. Maintainer environment.** The installed plugin here is 0.10.4 (phantom `lib:*` agents; 69/97 skills listed without a description). oh-my-claudecode 4.13.4 re-invokes finished subagents from its SubagentStop hook.

## 3. Principles for v2.0.0

1. **Evidence over attestation.** Gate verdicts are computed by code from artifacts (logs, result JSON, content hashes). Prompts consume verdicts; they do not produce them.
2. **One execution choke point.** Every tool and simulator call goes through the runner contract, which owns the backend (local, docker, ssh, lsf), environment (`env_source`, tool paths), license wait, timeouts and verdict capture.
3. **Configuration is consumed or removed.** Every `rat_config.json` field is read by the runner or dropped from the schema and docs.
4. **Prompts carry goals, contracts and reasons.** Exact scripts only where one sequence is safe.
5. **Measure before restructuring.** A plugin eval suite runs before and after every prompt or roster change.

  - If it is, count `teammate` entries in `background_tasks`, but only while a fresh RAT team config names this session as leader.
  - Today they do not count: the input has no idle flag, and an idle in-process teammate can stay "running".
- **Stop budgets are per project** (1a deferred re-review M5, extended by Task 12). Two sessions in one project share each gate's budget file.
  - The `prompt_id` check makes most interleavings hand over early.
  - A session whose last Stop yielded hands its no-progress count to the next session.
  - Fix: key the budget files by session id.
- **Rule 5 inside persistent loops** (1a final review I2). `/goal` and persistent-loop plugins (OMC ralph/ultrawork) keep one Stop chain going for a whole session, with tool calls between Stops, so Claude Code's block cap never ends it (it resets at every tool call).
  - Since 1a, the verify gate shows its notice again when the tracked RTL changes after the notice. But it never blocks again in that chain, so Claude is not told to verify the new edits.
  - Probe live: a `/goal` session with Edit allowed.
  - Option: re-arm the verify gate's block when the tracked RTL changes after the notice.
    - An RTL change implies a tool call, which resets Claude Code's counter.
    - Each block then needs a new edit, so the gate cannot loop on its own.
    - Decide with 1d, whose content hashes say exactly which changes are unverified.
- **Background simulations and the verify gate** (1a final review). A simulation started with `run_in_background` is a background shell, and shells do not pause the gates (1a Task 12). So the verify gate pushes while the simulation runs, then gives its notice. With 1d, a RAT runner can record that a run is in progress, and the gate can yield while that record is fresh.
- **Long background runs drop the completion loop** (1a final review M2). The skill gate measures staleness from `started_at`, and yields do not refresh it. If an orchestrator runs in the background for more than 2 hours, the first Stop that does not yield deletes its loop, without a notice.
  - Fix: count a yield as activity.
  - Show a one-time notice when a stale loop with pending criteria is removed.
- **A shared "pipeline waits for the user" check** (1a final review I1 residual). Since 1a, the skill gate hands over when the pipeline's own state shows `upper_spec_blocking` or `needs_user_decision`. `stop-gate.sh` also treats an exhausted gate ladder as a decision point, computed from its counters, and the skill gate does not mirror that. One helper that both hooks use would close the gap.
- **Observer agents pause the gates** (1a final review S1, reasoned only). Claude Code can auto-spawn an observer agent that an agent definition declares. It appears in `background_tasks` as a `subagent`, so every RAT gate yields while it runs. No RAT agent declares one, and the hook input carries no observer flag.
- **Symlinked state files** (1a final review M4, security). Hooks write `.rat/state` and `.rat/audit` files through symlinks.
  - A repository that commits such links can make every Stop truncate and rewrite a file the user owns, through 1a's budget files.
  - SessionStart already did this before 1a (`audit-util.sh`).
  - Fix: one write helper, used by every hook, that refuses a symlinked target or writes a temp file in the state directory and renames it.
- **Stop-gate cost without jq** (1a final review M5).
  - In python mode, a blocking Stop starts python about two dozen times in the skill gate and about 14 times in `stop-gate.sh`.
  - Because a timeout fails open, 1a raised those two hooks' timeouts to 10 s.
  - Fix: read each state file once per hook.
  - The gates also run the background-agent check twice per Stop (contracts review N5).
- **Hook code hygiene** (1a contracts review N2, N7).
  - The setup-marker check is written out four times: three in bootstrap and one in activation. Move it into `rat-dir-util.sh`.
  - `emit_post_continue` is the plain allow for every event, so it needs a clearer name.
- **Hook-owned team leader** (found by the 1a Task 7c review).
  - 1a Task 7c identifies sessions correctly, and judges config staleness by the file's mtime. But the leader id is still whatever the model wrote into `team-config.json`.
  - Three cases leave a real old leader in the config:
    - a run abandoned before teardown;
    - `/clear` in the leader, because a conversation reset regenerates the session id;
    - a mis-copied UUID.
  - In those cases every other session, the new leader included, skips all five Stop gates until the 2-hour bound.
  - Fix: a PostToolUse hook records the writer's `session_id`, and only from the main thread (no `agent_id`), whenever `team-config.json` is written. The gates trust that record, not the file's field.
  - The same record lets tmux and iTerm2 teammates keep a team alive (1a Task 7c deferral). They are separate sessions, so today their TaskUpdates do not refresh the config, and a team whose only activity is theirs goes stale after 2 hours.
- **PreToolUse:Skill writes before the permission decision** (found by 1a Task 9).
  - `rtl-phase-state-bootstrap.sh` writes at PreToolUse: it bootstraps compliance state (switching the phase and deleting the compliance report) and writes the spawn manifest.
  - So a phase-map skill call that the user rejects still leaves those writes behind. The P5B deny case is fixed in 1a.
  - Move these writes to PostToolUse:Skill, where the loop now starts.
  - Related (1a Task 9 review):
    - In coordinator mode, a read-only Skill result also starts a loop (rare; it did before Task 9 too).

- **Session fields from the hook-input root** (1a Task 8 follow-up; done in the 1a Task 10 follow-up). Every hook reads `cwd`, `agent_id`, `session_id`, `prompt_id` and `hook_event_name` through `jsonu_get_root_string` or `jsonu_session_id`, and `test_hooks_read_session_fields_from_the_input_root` pins it. - **Audit spawn counts** (found by the 1a Task 8 review).

  - The audit summary counts spawns by `spawn_start`, so it now counts orchestrators only.
  - Fix: record `spawn_start` for every RAT agent, and count spawns from `spawn_complete`.
- **Coverage-exclusion approval (with 1d).** The Task 7 reviews found two problems.
  - **The marker is global and permanent.** Nothing removes `.rat/state/coverage-exclusion-approved`. The gate's reason also hands Claude the approval command. So one self-approval, or one real approval, silently passes every later non-standard exclusion.
    - Fix: bind the approval to the exclusion set it approved. The recorded marker carries the set's fingerprint, and the gate compares it with the current set.
    - Record it through the approval flow rather than a bare `touch`, which is the same principle as runner-written verification evidence.
  - **The exclusion tables are read by grep.**
    - False positives: a copied policy legend, and "not ambiguous" in a reason.
    - Misses: "Out-of-scope", "Spec ambiguity", and a category in the last column.
    - Fix: base the count on a manifest or an approver column.

**Phase 2 — Truthful verdicts (alpha.2): #10, #11, #16, #17, #18, F9, F10.**
- Shared verdict classifier (bash + Python): PASS / FAIL / HANG / TIMEOUT / STALL / INCONCLUSIVE from exit status, log signatures and a completion marker. The precedence rules are a domain decision — owner: maintainer.
- SpyGlass: `set_option enableSV12 yes` + `-type verilog`, `incdir`/`define` mapping, `</dev/null`, Tcl error trap with a completion marker, goal-summary parsing.

- Synthesis: require a target library or an explicit opt-out (DC, Genus, PPA-Opt); align the Tcl-safety whitelist with the sibling wrappers.
- Phase 6 staleness after PPA-Opt (found by the 1a Task 4 review):
  - The Phase 6 gate's PPA re-review check runs only when `phase6-stale` exists, but the edit tracker skips `_check_p6_stale` for edits inside the PPA scope.
  - So a PPA patch newer than `design-note*.md` can pass without the re-review.
  - The second gap was that a present `phase6-cascade-done` bypassed the PPA check. That one is fixed in 1a Task 4 (`00ff6dc`).
- The sed JSON fallback cannot decode a `cwd` that contains `"` or `\`, so hooks fail open on such paths when neither jq nor Python is available. The 1a final reviews found more limits on the same path:
  - it drops nested state fields, so `stop-gate.sh` misses the autopilot's decision flags and tells Claude to continue;
  - it ends a tool-input string at the first `\"`, so a quoted Bash RTL edit goes untracked and Rule 5 fails open;
  - it returns the last occurrence of a root key before `tool_input` rather than the first. This is latent: no current input repeats a key.
  - Fix them together, or warn at SessionStart when neither parser is present. Today only PreToolUse:Skill warns.
- **User decisions yield to loop auto-continue** (found by the 1a Task 6 review). `stop-gate.sh` checks the ultraloop and the PPA loop before the autopilot. So a loop that is active inside its window hides the autopilot's upper-spec and user-decision notices, on every turn, until the loop state is removed.
  - The smallest fix makes both loop blocks yield when the autopilot state is live (present, within the staleness bound, not completed) and is waiting for a decision (`upper_spec_blocking` or `needs_user_decision`). It is about 20 lines and touches no exit, budget or allow path.
  - The review prototyped it, and 460 tests passed under sh and dash. It was deferred because no designed flow runs a loop and the autopilot together.
  - Pin the order between the two loop blocks at the same time.

## 5. Decisions

| ID | Question | Decision |
